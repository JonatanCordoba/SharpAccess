# Engineering-quality report

Every successful complete local verification ends by generating an exact-revision, offline report beneath `artifacts/quality-report`.

## Outputs

- `index.html`: self-contained report with sortable and filterable project, namespace, type, member, dependency, and hotspot tables.
- `metrics.json`: complete deterministic machine-readable dataset.
- `manifest.json`: revision, repository identity, tool versions, input hashes, and output hashes.
- `coverage/`: detailed local ReportGenerator line-by-line coverage pages.

The report must not load external JavaScript, CSS, fonts, analytics, or images, and it must not expose absolute workstation paths, usernames, secrets, connection strings, or machine-local identifiers.

## Metrics

The primary production scorecard covers `SharpAccess.Core`, `SharpAccess.Sqlite`, and `SharpAccess.Postgres`.

It includes line and branch coverage, CRAP score, source-based cyclomatic complexity, maintainability index, class coupling, project and namespace afferent/efferent coupling, external dependencies, and instability.

The report consumes coverage and complexity evidence already generated by the same verification run. It does not rerun the complete test suite. Existing coverage, changed-code coverage, complexity, analyzer, mutation, security, package, and provider gates remain enforced. Newly consolidated maintainability and coupling values are evidence-only until a reviewed baseline and ratchet policy are accepted.

Complete verification regenerates the Supported-provider aggregate from Core, SQLite, and PostgreSQL evidence, applies the PostgreSQL provider gate, and reruns changed-line and complexity analysis against that aggregate. Report generation fails when any production assembly declared by `eng/QualityReportPolicy.props` is absent or has no executable coverage evidence; missing projects are never silently excluded from repository percentages.

Schema version 2 distinguishes the total qualifying hotspot inventory from the configured top-N display count, records severity totals and machine-readable reason codes, reports adverse maintainability percentiles, exposes symbol-match status counts, and attributes partial types to every contributing source file. The HTML diagnostics and manifest hashes are generated deterministically from the same revision-bound evidence.

## Implementation ownership

`tools/SharpAccess.QualityReport` owns report generation, `scripts/quality-report.ps1` owns orchestration, and `eng/QualityReportPolicy.props` owns production scope and thresholds.

The implementation should be decomposed into focused argument, policy, Roslyn analysis, coverage parsing, complexity parsing, aggregation, statistics, HTML rendering, and manifest components. Decomposition must preserve deterministic ordering, paths, schemas, exclusions, hashes, and byte output unless an intentional reviewed schema change is made. Regression tests must compare complete machine-readable dataset and manifest semantics before and after the split.

Do not replace the local deterministic implementation with a hosted or proprietary analysis service.

## Commands

Run the report directly only after the prerequisite build, complete Supported-provider coverage, and complexity artifacts exist:

```powershell
./scripts/quality-report.ps1 -RepositoryRoot $PWD
```

Ordinary complete verification remains:

```powershell
./scripts/verify-local.ps1 -RepositoryRoot $PWD -Version '0.9.0-rc.1'
```
